## Part A：竞态条件 —— 先踩坑，再谈对错

### A1. 教科书 demo 已经骗不了你了

所有老教程都用这个证明「多线程不安全」：

```python
counter = 0
def work():
    global counter
    for _ in range(100_000):
        counter += 1        # 4 个线程跑完，理论上 < 400000
```

本机 3.13.9 实测（连 `sys.setswitchinterval(1e-6)` 都加了）：**3 次全是精确的
400000**。list、dict 版同样零丢失。

**这恰恰是最危险的结论**：「我测了，没错」≠ 线程安全。它只说明 3.13 的
抢占点恰好落不进 `+=` 这两三条字节码的窗口。

### A2. 真实业务形状的竞态：100% 复现

业务代码里「检查」和「动作」之间几乎不可能没有 I/O。把窗口撑开——
cache-aside 惰性初始化（get_or_create / 单例 / 缓存穿透全是这个形状）：

```python
cache = {}
init_calls = 0

def load_from_db(key):
    time.sleep(0.01)              # 模拟昂贵的数据库查询
    return f"value-{key}"

def get_bad(key):
    global init_calls
    if key not in cache:          # 检查
        init_calls += 1
        cache[key] = load_from_db(key)   # 动作（慢）——窗口大开
    return cache[key]

# 8 个线程 × 5 个不同的 key
```

实测：**期望初始化 5 次，实际 40 次**——每个线程都冲进了窗口，
8 倍重复查询。如果是写操作（扣库存、建订单），这就是资损。

修复：检查 + 动作整体加锁（double-checked locking 的朴素版）：

```python
def get_good(key):
    with init_lock:               # 锁的是「检查+动作」整个区间
        if key not in cache:
            cache[key] = load_from_db(key)
    return cache[key]
```

实测：恰好 5 次。✅

**工程要点：**
- 锁保护的是**不变量**（「没初始化才初始化」），不是某一行代码
- 判断哪里要锁的方法：找出所有「先读/查，后写」的相邻操作，
  中间夹着 I/O / 长计算的一律可疑
- `with lock:` 而不是 `lock.acquire()/release()`——异常路径不释放锁就是死锁

## Part B：GIL 的真相（两条实测）

| 场景 | 实测 | 结论 |
|---|---|---|
| CPU 密集：1 线程 0.61s，2 线程（各干同样的活） | **1.78s（2.91×）** | 线程不仅不加速，还倒贴——GIL 争抢 + 切换开销 |
| I/O 密集：串行 20 次请求 2.01s，`ThreadPoolExecutor(10)` | **0.21s（9.8×）** | 等 I/O 时 GIL 释放，线程是真并发 |

**选型直觉**：你的代码大部分时间在「等」（网络/磁盘/子进程）→ 线程有效；
大部分时间在「算」→ 线程无效甚至负优化，上多进程（或_numpy/C 扩展把算力
下沉到 C 层——那里释放 GIL）。

## Part C：完整组件——多线程批量上报器（BatchShipper）

真实场景：Web 服务里埋点/日志要上报，不能每条一个 HTTP 请求（打挂下游），
也不能丢。标准解法：任意线程投递 → **唯一**后台线程攒批 → 按条数/时间双阈值
触发发送 → 关闭时清空不丢数据。

```python
import threading, queue, time
from dataclasses import dataclass


@dataclass(slots=True)
class Record:
    level: str
    msg: str


class BatchShipper:
    """多线程安全的后台批量上报器：攒一批再发（按条数或按时间触发）。"""

    def __init__(self, batch_size=100, flush_interval=0.5, maxsize=10_000, sink=None):
        self._q: queue.Queue[Record] = queue.Queue(maxsize=maxsize)  # ① 有界=背压
        self._stop = threading.Event()                                # ② 关闭信号
        self._batch_size = batch_size
        self._interval = flush_interval
        self._sink = sink or (lambda batch: None)   # 真实场景: HTTP POST / 批量写库
        self._drop_count = 0
        self._thread = threading.Thread(
            target=self._run, name="BatchShipper", daemon=True)      # ③ 守护线程
        self._thread.start()

    # ---- 生产者侧（任意线程调用都安全）----
    def submit(self, record: Record) -> None:
        try:
            self._q.put(record, timeout=1.0)   # ④ 队列满则阻塞：压力传回生产者
        except queue.Full:
            self._drop_count += 1              #    或丢弃+计数，二选一，别静默

    # ---- 消费者（唯一的后台线程）----
    def _run(self) -> None:
        batch: list[Record] = []
        last_flush = time.monotonic()
        while not self._stop.is_set():
            try:
                # ⑤ 带超时的 get：空闲时按时间刷新，同时能及时响应关闭
                batch.append(self._q.get(timeout=0.05))
                self._q.task_done()
            except queue.Empty:
                if batch and time.monotonic() - last_flush >= self._interval:
                    self._safe_deliver(batch)
                    batch, last_flush = [], time.monotonic()
                continue
            if len(batch) >= self._batch_size:
                self._safe_deliver(batch)
                batch, last_flush = [], time.monotonic()
        # ⑥ 收到关闭信号：清空剩余再退出（不丢数据）
        while True:
            try:
                batch.append(self._q.get_nowait())
                self._q.task_done()
            except queue.Empty:
                break
        if batch:
            self._safe_deliver(batch)

    def _safe_deliver(self, batch: list[Record]) -> None:
        """⑦ 线程里的异常不会传到主线程，必须自己接住，否则线程静默死亡。"""
        try:
            self._sink(batch)
        except Exception:
            pass                # 真实场景: 重试队列 / 计数+告警，绝不让 worker 死

    # ---- 关闭（支持 with）----
    def close(self, timeout: float = 5.0) -> bool:
        self._stop.set()
        self._thread.join(timeout)
        return not self._thread.is_alive()     # False = 没能优雅退出

    def __enter__(self):
        return self

    def __exit__(self, *exc):
        return None                            # 不吞异常，只负责收尾
```

### 验证结果（本机实测）

| 测试 | 结果 |
|---|---|
| T1：4 生产者线程共 1000 条，batch_size=100 | 恰好 10 批 / 1000 条，无丢失无错乱 |
| T2：只投 3 条，等 flush_interval 到点 | 时间阈值触发，发出 1 批 [3] |
| T3：投 57 条后**立刻** close | 优雅退出=True，剩余 57 条全部发出 |

### 七个工程决策点（①~⑦）

1. **有界队列 = 背压**：下游变慢 → 队列堆满 → `put` 阻塞 → 生产者被迫减速。
   无界队列 = 内存炸弹，故障时 OOM 而不是变慢。
2. **`Event` 而不是 `while True + sleep`**：关闭信号立刻可见；`Event.is_set()`
   检查是廉价的原子操作。
3. **daemon=True 的取舍**：主进程崩溃时不被后台线程拖住（快速失败）。
   代价是可能丢数据——所以正常路径必须走 `close()`，daemon 只是最后保险。
4. **满时阻塞还是丢弃是业务决策**：埋点可丢、订单不可丢。但都要**可观测**
   （计数），静默丢弃是事故。
5. **`get(timeout=...)` 一石三鸟**：等数据 / 空闲时按时钟触发 flush / 及时
   响应关闭。单独起一个 Timer 线程做定时 flush 是更复杂的错误答案。
6. **优雅关闭三步**：`stop.set()` → 排干队列 → join(timeout) 并检查返回值。
   join 超时不代表成功，要看线程是否真的死了。
7. **线程异常必须自己接**：worker 线程抛异常不会传播到任何地方，
   线程死掉后系统「看起来正常地」停止工作——最难查的故障形态。

## Part D：什么时候不要自己写

| 需求 | 正确工具 | 原因 |
|---|---|---|
| 一批 I/O 任务并发跑完拿结果 | `ThreadPoolExecutor` + `as_completed` | 20 行手写循环 → 3 行，异常/超时/结果收集全内置 |
| 高并发 I/O（千级连接） | `asyncio` | 线程是 MB 级栈内存，协程是 KB 级；`async/await` 无锁心智负担 |
| CPU 密集加速 | `ProcessPoolExecutor` / numpy / C 扩展 | 绕开 GIL（实测线程反而慢 2.91×） |
| 跨进程/跨机器的任务队列 | Celery / RQ + Redis | 进程内队列活不过一次重启 |
| 本文的攒批上报 | 自己写（本文）或看 logging.handlers.QueueHandler 的源码 | 标准库里就有同款设计，值得一读 |

**一个实用的判断顺序**：先问「I/O 还是 CPU」→ I/O 问「并发量级」
（几十 → 线程池；上千 → asyncio）→ 最后才问「要不要进程内队列/攒批」。
